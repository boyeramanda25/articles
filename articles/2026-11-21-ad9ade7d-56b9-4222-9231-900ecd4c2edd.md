# 用幂等键防止设备重复提交

<!-- content-workspace-job:ad9ade7d-56b9-4222-9231-900ecd4c2edd -->

## 问题场景

设备的创建接口在超时重试时被调了两次，用户看到两条记录。前端加了防抖，但网络重试和网关重放照样能打进来。

## 实现步骤

客户端带一个请求 id，服务端用 setIfAbsent 抢占，抢不到直接返回重复。

```java
String key = "idem:" + req.getRequestId();
Boolean ok = redis.opsForValue()
    .setIfAbsent(key, "1", Duration.ofMinutes(10));
if (Boolean.FALSE.equals(ok)) {
    return Resp.duplicate();
}
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
```

数据库侧再加唯一约束，防止 Redis 失效时出现漏网。

处理成功后才写结果缓存，中途异常要释放占位，否则会卡住重试。

```java
System.out.println(redis.hasKey(key));
System.out.println(redis.getExpire(key));
```

## 验证方法

用同一个请求 id 连发两次，第二次应返回重复提示且表里只有一行。

## 注意事项

幂等键的有效期要覆盖重试窗口，太短起不到作用；占位与业务写入不在同一事务里，异常分支必须显式删除占位。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

在迁移过程中，可以通过压测确认容量水位，避免资源被长期占用。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确认指标平稳后再逐步放开。

对于刚接手的同学，要明确各项资源的释放时机，确保线上行为始终可控。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

如果数据量继续增长，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

在压测阶段，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。
