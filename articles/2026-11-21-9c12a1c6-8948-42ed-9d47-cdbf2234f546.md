# 用 Makefile 固化etl的构建与检查命令

## 问题场景

etl仓库的构建命令写在文档里，参数有七八个，复制粘贴经常漏掉 race 检测，本地过了 CI 挂。

## 实现步骤

把构建、测试、检查都定义成目标，参数写在目标里，不靠记忆。

```makefile
APP := etl
.PHONY: build test lint fmt

build:
	go build -o bin/$(APP) ./cmd/$(APP)

test:
	go test ./... -race -count=1
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
```

声明 PHONY，避免目录同名导致目标不执行。

```makefile
lint:
	golangci-lint run ./...

fmt:
	gofmt -l -w .
```

本地和 CI 调同一个目标，环境差异只剩运行时。

```bash
make build
make test
make lint
```

## 验证方法

在干净环境执行 make build 与 make test，应能一次通过且无需额外参数。

## 注意事项

Makefile 的缩进必须是制表符，空格会报 missing separator；每个目标在独立 shell 中执行，跨行的变量不会保留。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

在压测阶段，尽量把决策依据写进变更说明，便于横向对比不同方案的效果。

从排障效率看，要明确各项资源的释放时机，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

在跨团队协作时，建议在变更前留一份可回滚的快照，便于横向对比不同方案的效果。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。
