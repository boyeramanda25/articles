# 用分区表归档任务表的历史数据

<!-- content-workspace-job:f767946e-4f23-4921-9ce2-c836cf6fee83 -->

## 问题场景

任务表积累了几亿行历史数据，DELETE 老数据要跑几个小时，还产生大量 WAL，删完之后磁盘空间也不释放。

## 实现步骤

按时间范围建分区，每个分区对应一个时间段。

```sql
CREATE TABLE tasks_202611 PARTITION OF tasks
FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
```

归档时把整个分区从主表摘下来，元数据操作，瞬间完成。

```sql
ALTER TABLE tasks DETACH PARTITION tasks_202601;
```

查分区列表确认挂载关系，摘除后主表查询自动跳过该段。

```sql
SELECT inhrelid::regclass
FROM pg_inherits WHERE inhparent = 'tasks'::regclass;
```

## 注意事项

分区键必须出现在查询条件里才能裁剪，否则照样扫全部分区；主表上的唯一索引必须包含分区键，这是常见的建表失败原因。

从成本角度看，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

上线初期，要把边界条件列成清单逐项确认，以便后续复盘有据可查。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，让排查路径更短。

针对这类偶发问题，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

在压测阶段，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

从排障效率看，要明确各项资源的释放时机，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。
