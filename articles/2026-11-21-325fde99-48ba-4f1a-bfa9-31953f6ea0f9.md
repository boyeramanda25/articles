# 读懂工单表查询的 EXPLAIN ANALYZE 输出

<!-- content-workspace-job:325fde99-48ba-4f1a-bfa9-31953f6ea0f9 -->

## 问题场景

工单表的接口慢，看执行计划觉得没问题，因为看的是预估。预估行数和实际差了两个数量级，优化器据此选错了连接方式。

## 实现步骤

加 ANALYZE 拿到真实执行数据，逐节点的 actual time 是排查重点。

```sql
EXPLAIN ANALYZE SELECT * FROM tickets WHERE priority > 90;
```

加 BUFFERS 看缓存命中，大量读磁盘说明缓存不够或扫描过多。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM tickets WHERE priority > 90;
```

对比预估与实际行数，差距大就更新统计信息或调大采样比例。

```sql
SELECT relname, seq_scan, idx_scan
FROM pg_stat_user_tables WHERE relname = 'tickets';
```

## 注意事项

ANALYZE 会真实执行语句，写操作不要直接加；采样统计对倾斜数据不准，必要时对特定列调高统计目标。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在压测阶段，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

如果数据量继续增长，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

在压测阶段，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。

上线初期，要把异常路径和正常路径分别覆盖一遍，以便快速定位瓶颈。

从成本角度看，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。
