# 用 outbox 模式保证账务事件不丢

<!-- content-workspace-job:a861cc46-d7d5-46d9-88c8-1e0b7b49fb08 -->

## 问题场景

账务下单后要发消息通知下游，代码里先写库再发 MQ。中间进程崩溃，库里有了订单但消息没发出去，下游永远收不到。

## 实现步骤

在业务表旁边建一张 outbox 表，与业务写入放在同一个事务里。

```sql
INSERT INTO outbox (id, topic, payload, status)
VALUES (?, ?, ?, 'new');
```

独立线程轮询未投递的记录，发送成功再标记，失败保留待重试。

```java
@Transactional
public void place(Account o) {
    repo.save(o);
    outbox.save(event(o));
}
```

多实例轮询时用 SKIP LOCKED 避免重复取同一条。

```sql
SELECT id, payload FROM outbox
WHERE status = 'new' ORDER BY id LIMIT 100
FOR UPDATE SKIP LOCKED;
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
```

## 注意事项

outbox 表会持续增长，要配定期清理；下游必须能处理重复消息，至少一次投递无法保证只发一次。

在实际落地时，建议先在小流量环境验证行为是否符合预期，减少不必要的返工成本。

对稳定性要求高的场景，需要评估对现有调用方的影响面，并同步给相关方知会。

在多人协作的项目里，应当拆分步骤以便中途校验，让新人上手时少走弯路。

在压测阶段，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。

上线初期，要把异常路径和正常路径分别覆盖一遍，以便快速定位瓶颈。

从成本角度看，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

对稳定性要求高的场景，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

上线初期，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

在实际落地时，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。
