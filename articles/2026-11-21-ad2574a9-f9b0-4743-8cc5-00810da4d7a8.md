# 用令牌桶给评论接口做限流

<!-- content-workspace-job:ad2574a9-f9b0-4743-8cc5-00810da4d7a8 -->

## 问题场景

评论的开放接口被合作方在整点集中调用，瞬时流量是平时的二十倍，下游直接被压垮。简单的固定窗口计数又会在窗口边界放过两倍流量。

## 实现步骤

令牌桶按固定速率补充令牌，桶容量就是允许的突发量。

```go
limiter := rate.NewLimiter(rate.Limit(100), 200)
if !limiter.Allow() {
    http.Error(w, "slow down", http.StatusTooManyRequests)
    return
}
```

按调用方维度分桶，避免一个客户把额度占满影响其他人。

```go
var (
    mu      sync.Mutex
    buckets = map[string]*rate.Limiter{}
)

func of(key string) *rate.Limiter {
    mu.Lock()
    defer mu.Unlock()
    l, ok := buckets[key]
    if !ok {
        l = rate.NewLimiter(rate.Limit(20), 40)
```

## 验证方法

以远超限额的速率压测，通过的请求数应稳定在设定速率附近。

## 注意事项

分桶表的键要设过期，否则海量调用方会把内存撑爆；限流是保护手段，被限流的请求要能快速失败，不能让它继续占用连接。

在资源受限的环境下，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

结合团队现状，可以通过日志补充上下文信息，同时把结论沉淀进团队文档。

遇到复杂链路时，先把最小可复现的用例固定下来，让排查路径更短。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

针对这类偶发问题，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。
