# 仓库字典查询加上缓存后减少重复计算

<!-- content-workspace-job:29230a0a-91a4-46b0-8f3b-af0b8b26e44e -->

## 问题场景

每次渲染仓库详情都要重复计算同一组派生字段，调用量一上来 CPU 就被同一段逻辑吃掉。

## 实现步骤

把派生逻辑抽成只依赖入参的纯函数，加 lru_cache 并设定合理容量。

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def summary(ident, version):
    rows = fetch_rows(ident)
    return {"id": ident, "total": sum(r["capacity"] for r in rows), "v": version}
```

数据变更时主动调用 cache_clear，或把版本号作为入参的一部分。

```python
def invalidate():
    summary.cache_clear()
    return summary.cache_info().currsize
```

监控缓存命中率，命中率长期偏低说明入参过于分散，缓存没有意义。

```python
a = summary("warehouse-1", 1200)
b = summary("warehouse-1", 1200)
print(a == b, summary.cache_info().hits)
```

## 验证方法

连续调用同一参数两次，第二次的耗时应显著低于第一次，且返回值完全一致。

## 注意事项

lru_cache 要求入参可哈希，传列表会直接报错；缓存会延长对象生命周期，大对象要设 maxsize。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，并保留回滚开关以便快速恢复。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使运维成本保持在合理区间。

对于刚接手的同学，要明确各项资源的释放时机，并同步给相关方知会。

结合团队现状，可以通过压测确认容量水位，让新人上手时少走弯路。

在资源受限的环境下，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。
