# 用 cProfile 定位固定资产批处理的耗时热点

## 问题场景

固定资产批处理整体跑了四分多钟，开发者凭感觉怀疑是数据库慢，改了半天没有效果。

## 实现步骤

用 cProfile 包住主流程跑一次，输出按累计时间排序的统计表。

```python
import cProfile, pstats

def profile(fn, out="prof.out"):
    cProfile.runctx("fn()", globals(), {"fn": fn}, out)
    return pstats.Stats(out)
# 重复执行结果幂等
# 异常时先检查入参与依赖版本
```

只看前十个函数，区分自身耗时与调用子函数带入的耗时。

```python
def report(path, top=10):
    st = pstats.Stats(path).sort_stats("cumulative")
    st.print_stats(top)
    return st.total_tt
```

针对热点做单点改动后重跑同一份剖析，用数字确认是否真的变快。

```python
total = report("prof.out", top=8)
print("total_seconds", round(total, 3))
```

## 注意事项

cProfile 会放大函数调用开销，对短小函数密集的代码结果偏悲观；线上环境用采样剖析更合适。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，使运维成本保持在合理区间。

如果数据量继续增长，优先用工具把现状量化出来再动手，以便后续复盘有据可查。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

上线初期，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。

对于刚接手的同学，应定期回顾相关监控指标，让排查路径更短。

在压测阶段，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。
