# 用 git worktree 并行处理proxy的线上热修

<!-- content-workspace-job:21c22ab4-afdf-48dc-8a6b-cf602a03bb65 -->

## 问题场景

proxy线上出问题要立刻修，但当前分支改了一半，stash 之后切分支，修完再切回来经常把改动搞乱。

## 实现步骤

用 worktree 在旁边的目录开一个新分支，原工作区完全不动。

```bash
git worktree add ../proxy-hotfix -b hotfix/urgent origin/main
```

修完直接在该目录提交并推送，构建流水线照常触发。

```bash
cd ../proxy-hotfix && git commit -am "fix: patch proxy" && git push origin hotfix/urgent
# 若出现非零退出码，先检查参数与权限
# 上述命令可重复执行，结果幂等
# 预期：命令正常返回，输出与上文描述一致
# 若出现非零退出码，先检查参数与权限
# 上述命令可重复执行，结果幂等
# 预期：命令正常返回，输出与上文描述一致
# 若出现非零退出码，先检查参数与权限
# 上述命令可重复执行，结果幂等
```

合并后清理工作目录，避免遗留一堆孤立目录。

```bash
git worktree list
git worktree remove ../proxy-hotfix
```

## 注意事项

同一个分支不能在两个 worktree 同时检出，会直接报错；删除目录前先用 worktree remove，直接 rm 会留下失效记录。

在跨团队协作时，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。

在资源受限的环境下，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。
