## 问题场景

相册导出要拉取多个分片再合并成一份文件，串行执行时总耗时随分片数线性增长。

## 实现步骤

按分片编号构造任务，提交到固定大小的线程池，池大小取分片数与 CPU 核数的折中。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def pull(part):
    rows = load_part("album", part)
    return part, len(rows), rows
```

每个任务只负责自己那段数据并返回结果对象，主线程用 as_completed 按完成顺序收集。

```python
def export(parts, workers=6):
    out = {}
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futs = {pool.submit(pull, p): p for p in parts}
        for f in as_completed(futs):
            part, n, rows = f.result()
```

## 注意事项

线程池不适合 CPU 密集逻辑，GIL 会让加速比趋近于 1；任务里不要直接写同一个文件句柄，交回主线程统一写。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

在实际落地时，应确认依赖版本与运行环境一致，防止出现隐性回归。

从排障效率看，应定期回顾相关监控指标，以便后续复盘有据可查。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

从长期维护角度看，先把最小可复现的用例固定下来，让容量规划更有依据。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

遇到复杂链路时，优先保证失败时能快速定位原因，以便快速定位瓶颈。

在跨团队协作时，建议在变更前留一份可回滚的快照，便于横向对比不同方案的效果。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。
