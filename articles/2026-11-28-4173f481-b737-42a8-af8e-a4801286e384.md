# 报销单请求失败时按状态码分流重试

<!-- content-workspace-job:4173f481-b737-42a8-af8e-a4801286e384 -->

## 问题场景

报销单列表接口偶发 502，前端统一无脑重试三次，遇到参数错误时也重试，白白放大流量。

## 实现步骤

把状态码分成可重试与不可重试两类，只有 5xx 与超时进入重试。

```javascript
const RETRY = new Set([502, 503, 504]);
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
```

重试间隔按指数增长并加随机抖动，避免同一时刻大量请求打到同一实例。

```javascript
async function get(url, tries = 3) {
  let last;
  for (let i = 0; i < tries; i++) {
    const res = await fetch(url);
    if (res.ok) return res.json();
    last = res.status;
    if (!RETRY.has(res.status)) break;
    await sleep(300 * 2 ** i + Math.random() * 100);
  }
  throw new Error('expense 请求失败: ' + last);
}
```

## 验证方法

用桩服务分别返回 400 与 503，前者应只请求一次，后者应按次数重试后失败。

## 注意事项

POST 请求重试要保证幂等，否则可能重复写入；登录失效类 401 不能重试，应直接跳转。

对稳定性要求高的场景，需要评估对现有调用方的影响面，以便快速定位瓶颈。

上线初期，要把异常路径和正常路径分别覆盖一遍，减少不必要的返工成本。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

在资源受限的环境下，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，避免问题积累到难以收场。

结合历史事故记录，要把边界条件列成清单逐项确认，降低同类问题再次发生的概率。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

在跨团队协作时，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。

遇到复杂链路时，优先保证失败时能快速定位原因，减少不必要的返工成本。
