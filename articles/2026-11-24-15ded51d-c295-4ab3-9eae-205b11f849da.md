## 问题场景

车辆批处理整体跑了四分多钟，开发者凭感觉怀疑是数据库慢，改了半天没有效果。

## 实现步骤

用 cProfile 包住主流程跑一次，输出按累计时间排序的统计表。

```python
import cProfile, pstats

def profile(fn, out="prof.out"):
    cProfile.runctx("fn()", globals(), {"fn": fn}, out)
    return pstats.Stats(out)
# 异常时先检查入参与依赖版本
```

只看前十个函数，区分自身耗时与调用子函数带入的耗时。

```python
def report(path, top=10):
    st = pstats.Stats(path).sort_stats("cumulative")
    st.print_stats(top)
    return st.total_tt
```

针对热点做单点改动后重跑同一份剖析，用数字确认是否真的变快。

```python
total = report("prof.out", top=8)
print("total_seconds", round(total, 3))
```

## 注意事项

cProfile 会放大函数调用开销，对短小函数密集的代码结果偏悲观；线上环境用采样剖析更合适。

从长期维护角度看，优先保证失败时能快速定位原因，并同步给相关方知会。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

在实际落地时，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

从成本角度看，应当拆分步骤以便中途校验，让新人上手时少走弯路。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。
