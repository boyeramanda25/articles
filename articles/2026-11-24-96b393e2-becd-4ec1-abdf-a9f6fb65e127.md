## 问题场景

司机批处理整体跑了四分多钟，开发者凭感觉怀疑是数据库慢，改了半天没有效果。

## 实现步骤

用 cProfile 包住主流程跑一次，输出按累计时间排序的统计表。

```python
import cProfile, pstats

def profile(fn, out="prof.out"):
    cProfile.runctx("fn()", globals(), {"fn": fn}, out)
    return pstats.Stats(out)
# 预期：输出与上文描述一致
```

只看前十个函数，区分自身耗时与调用子函数带入的耗时。

```python
def report(path, top=10):
    st = pstats.Stats(path).sort_stats("cumulative")
    st.print_stats(top)
    return st.total_tt
```

针对热点做单点改动后重跑同一份剖析，用数字确认是否真的变快。

```python
total = report("prof.out", top=8)
print("total_seconds", round(total, 3))
```

## 注意事项

cProfile 会放大函数调用开销，对短小函数密集的代码结果偏悲观；线上环境用采样剖析更合适。

上线初期，要把异常路径和正常路径分别覆盖一遍，确认指标平稳后再逐步放开。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

如果数据量继续增长，需要评估对现有调用方的影响面，减少不必要的返工成本。

从成本角度看，应当拆分步骤以便中途校验，避免资源被长期占用。

在实际落地时，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。
