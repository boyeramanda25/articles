# 优惠券表按discount查询用不上索引的几种写法

<!-- content-workspace-job:ddf242bb-a43d-483b-bb5f-7b52c73b0bd9 -->

## 问题场景

优惠券表在discount上明明建了索引，按日期查还是全表扫描。把语句拿出来看，条件里对列做了函数运算，索引自然用不上。

## 实现步骤

定位问题：条件里出现函数、算术运算或类型不一致，索引都会失效。

```sql
EXPLAIN SELECT * FROM coupons WHERE DATE(created_at) = '2026-01-01';
```

把运算挪到常量侧，改成范围比较，索引就能正常命中。

```sql
SELECT * FROM coupons
WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02';
```

用 EXPLAIN 确认 type 从 ALL 变成 range，rows 明显下降。

```sql
EXPLAIN SELECT * FROM coupons WHERE discount + 0 > 60;
CREATE INDEX idx_discount ON coupons (discount);
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
```

## 注意事项

字符串列与数字比较会触发隐式转换，同样失效；LIKE 只有前缀匹配能走索引；OR 连接不同列时优化器可能直接放弃索引。

在多人协作的项目里，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使运维成本保持在合理区间。

对于刚接手的同学，要明确各项资源的释放时机，并同步给相关方知会。

结合团队现状，可以通过压测确认容量水位，让新人上手时少走弯路。

在资源受限的环境下，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。
