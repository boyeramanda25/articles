# 任务字典查询加上缓存后减少重复计算

<!-- content-workspace-job:6c1ae4cd-3ac7-4666-ae9b-d4e57fa59fd6 -->

## 问题场景

每次渲染任务详情都要重复计算同一组派生字段，调用量一上来 CPU 就被同一段逻辑吃掉。

## 实现步骤

把派生逻辑抽成只依赖入参的纯函数，加 lru_cache 并设定合理容量。

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def summary(ident, version):
    rows = fetch_rows(ident)
    return {"id": ident, "total": sum(r["retry"] for r in rows), "v": version}
```

数据变更时主动调用 cache_clear，或把版本号作为入参的一部分。

```python
def invalidate():
    summary.cache_clear()
    return summary.cache_info().currsize
```

监控缓存命中率，命中率长期偏低说明入参过于分散，缓存没有意义。

```python
a = summary("task-1", 3)
b = summary("task-1", 3)
print(a == b, summary.cache_info().hits)
```

## 注意事项

lru_cache 要求入参可哈希，传列表会直接报错；缓存会延长对象生命周期，大对象要设 maxsize。

在迁移过程中，可以通过日志补充上下文信息，同时把结论沉淀进团队文档。

结合团队现状，可以通过日志补充上下文信息，保证每一步都可验证。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

上线初期，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。

对于刚接手的同学，应定期回顾相关监控指标，让排查路径更短。

在压测阶段，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。
