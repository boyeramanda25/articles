# 给用户的 WebSocket 连接加心跳保活

<!-- content-workspace-job:49d6cdad-1496-4cf7-a237-8e4a876678a6 -->

## 问题场景

用户的实时通知经常延迟几十秒才到，客户端以为自己还连着，其实连接早已被负载均衡器静默断开，浏览器还没触发 close 事件。

## 实现步骤

客户端定时发心跳，服务端收到就回，形成双向确认。

```typescript
const ws = new WebSocket(url);
ws.onopen = () => setInterval(() => ws.send(JSON.stringify({ type: "ping" })), 25000);
```

用标记位判断上一轮是否有响应，没有就主动关闭重连。

```typescript
let alive = true;
ws.onmessage = () => { alive = true; };
setInterval(() => {
  if (!alive) ws.close();
  alive = false;
}, 60000);
```

服务端的探活间隔要小于中间设备的空闲超时，否则还是会被切断。

```typescript
wss.on("connection", (s) => {
  s.isAlive = true;
  s.on("pong", () => { s.isAlive = true; });
});
```

## 验证方法

挂机十分钟后发一条消息，应能立即收到；人为断网后客户端应在两个周期内触发重连。

## 注意事项

浏览器不会因为网络中断立刻触发 close，只靠事件判断连接状态并不可靠；心跳频率过高会增加无谓流量，通常二十到三十秒一次比较合适。

从成本角度看，应当限定作用范围避免影响其他业务，保证每一步都可验证。

在多人协作的项目里，应当限定作用范围避免影响其他业务，避免问题积累到难以收场。

在跨团队协作时，要避免在高峰期执行这类操作，使整体改动风险可控。

从排障效率看，要明确各项资源的释放时机，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。
